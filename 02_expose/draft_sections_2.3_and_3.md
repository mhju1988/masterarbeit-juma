## 2.3 Research gap

The evaluation of correctness in generated queries is well developed. Text-to-SQL benchmarks such
as Spider and BIRD pair natural-language questions with expert-written reference queries, and
execution accuracy has become a standard measure. Recent work has begun to question the reference
queries themselves: Jin et al. (2026) report substantial annotation error rates in widely used
benchmarks, which affects correctness scores and, more importantly here, any comparison that treats
gold queries as a record of how people write SQL.

Whether models write SQL *differently* from people has received less attention, although it is no
longer unexamined. Pecuchova and Benko (2026) compared 669 Snowflake solutions to shared analytical
tasks — 189 written by people, 480 generated by three model families under four prompt
formulations — and found the generated queries significantly higher on nesting depth, subquery use,
aggregate use, common table expression use and composite complexity. Prompting that encouraged
decomposition reliably increased the use of common table expressions. Their study establishes that
the difference exists and that it is sensitive to how the model is asked.

It also shows where the question currently stops, in three respects.

**The measures come from software engineering.** Lines of code, Halstead vocabulary and difficulty,
cognitive complexity. These describe text. They are indifferent to relational semantics, so two
queries with identical scores can produce entirely different execution plans, and a formulation that
a code metric treats as the simpler one may be precisely the formulation that prevents an index from
being used.

**Nothing is executed.** Queries are analysed in the form in which they were written — the authors
note that they do not map equivalent formulations to a canonical representation — and neither
execution plans nor the physical design of the database enter the analysis.

**The human side is student work.** 189 answers from 30 participants in a graded assessment,
retained when scored at least four of five points, which the authors describe as an inclusion filter
rather than a correctness measure. They treat this as the study's principal limitation and call for
the human baseline to be extended to professional developers.

Two gaps follow from this.

**Construct usage has been counted flat.** Existing comparisons report how often subqueries, common
table expressions or window functions occur, but not what those counts mean. SQL did not arrive
complete: it accumulated its capabilities across successive revisions of the standard, and a task
solved with a correlated subquery is often one that a later revision made expressible in another
way. Relating construct choice to that development turns a set of frequencies into a statement about
which parts of the language each author actually uses — and, for generated queries, about which
parts of the language a model has effectively learned to use. To the best of the author's knowledge
this relation has not been examined.

**The observed differences have not been traced to their consequences.** A difference in the query
text need not be a difference in behaviour. The optimizer rewrites queries, and two formulations may
converge on the same execution plan, in which case a structural finding is a stylistic observation
and nothing more. Where they do not converge, the reason frequently lies in the physical design: a
predicate that wraps a column in a function is not the same query for an optimizer that has an index
on that column, even though it returns the same rows. Whether the structural differences between
human-written and generated SQL survive optimization — and whether the available indexes decide when
they matter — is open.

This thesis addresses both. It measures construct usage against the development of the language
itself, and then tests whether the differences it finds have consequences at the level of the
execution plan and the physical design. Because the comparison depends on what the human side
actually represents, it draws that side from corpora of working SQL rather than from assessment
answers or benchmark annotations — the extension Pecuchova and Benko name as the next step.

## 3 Research questions

**Main question**

> How do large language models use SQL as a language compared with human authors, and do the
> differences that appear in the query text still matter once the query is optimized and executed?

**RQ1 — Language structure.**
Which constructs do model-generated and human-written queries use, and how do they differ in
composition (*Aufbau*), operator choice (*Operatoren*), and the expression of logic (*Logik*)?
Answering this requires only the query text: both corpora are parsed and their structural profiles
compared.

**RQ2 — Evolution of the language.**
Where do those constructs sit in the development of SQL — do models make use of the language's more
recent capabilities, or do they reproduce older idioms? Each construct is assigned to the revision
of the standard that introduced it, and the two distributions are compared.

**RQ3 — Optimizer.**
Do the structural differences survive optimization, or does the optimizer reduce differently phrased
queries to the same execution plan? Both queries of a pair are executed and their plans compared
through `EXPLAIN (ANALYZE, BUFFERS)`.

**RQ4 — Physical design.**
Does the physical design decide when phrasing matters — can a generated query make use of the
indexes that are available, and does adding or removing an index change the answer to RQ3? The same
query set is run under different index configurations, with the index configuration treated as an
experimental variable rather than a fixed setting.

RQ1 and RQ2 concern the language and form the core of the work. RQ3 and RQ4 establish whether the
differences they identify have any effect, and can only be answered once RQ1 has been answered.

**Correctness is not a research question.** Current models handle correctness on established
benchmarks well enough that a correctness result would be unsurprising, and comparing the structure
of queries that return different results would compare a formulation against a mistake. Correctness
therefore serves as the inclusion criterion: only queries whose results match those of the reference
query enter the structural comparison. It is reported, but as a property of the sample rather than
as a finding.

A further question follows from the results rather than guiding the measurements, and the discussion
returns to it: if a growing share of SQL is written by models rather than by people, what does the
observed usage suggest about the direction in which the language itself should develop?
