## 1. Summary

The exposé was approved on 7 August 2026. Since then the first exploratory phase described in it
(phase E1) has been carried out: the reference corpus was obtained and its queries were measured
before any measurement infrastructure was built.

All 500 gold queries of the BIRD Mini-Dev benchmark have been parsed and profiled along the three
dimensions set out in the exposé — composition (*Aufbau*), operators (*Operatoren*) and logic
(*Logik*). The static-analysis layer of the harness exists and runs. No database is required for
it.

Four results came out of this, one of them unexpected. The closest related publication has also
been obtained and read in full, which allows the thesis to be positioned against it with evidence
rather than assumption.

In parallel, a **pilot of the full pipeline** was carried out on Spider 1.0, which ships its
databases and schemas. Thirty tasks over twenty databases were put to two models, the generated SQL
was executed, and its results were compared with the reference. A first paired human-versus-model
structural comparison therefore exists, together with a set of counterexample tests showing that two
formulations which agree on the benchmark data can diverge under NULLs and ties.

Registration has not yet taken place. The reason is the credit-point requirement for admission, not
the exposé.

## 3. Results

### 3.1 The reference queries are structurally plain

| | queries | share |
|---|---|---|
| no subquery nesting at all | 436 | 87.2 % |
| one level of nesting | 58 | 11.6 % |
| two or more levels | 6 | 1.2 % |
| at least one join | 407 | 81.4 % |
| common table expressions | 6 | 1.2 % |
| window functions | 5 | 1.0 % |
| set operations | 2 | 0.4 % |

The characteristic gold query is a single join with an aggregate and no nesting; 124 queries match
that shape exactly. Almost everything in the set is expressible in SQL-92.

**Relevance.** This gives RQ2 a measured floor. A generated corpus that uses window functions or
CTEs at any appreciable rate stands in immediate contrast to a 1 % baseline.

**Open question.** Whether the set is plain because people write that way, or because a benchmark
annotator writes the simplest query that returns the correct rows, cannot be decided from this
corpus alone.

### 3.2 The PostgreSQL variant is a machine port

This was not expected and it affects the method.

| marker | queries | share |
|---|---|---|
| `NULLIF(…, 0)` division guards | 96 | 19.2 % |
| `NULLS LAST` / `NULLS FIRST` added to `ORDER BY` | 84 | 16.8 % |
| `::` cast operator | 9 | 1.8 % |
| `SPLIT_PART` | 4 | 0.8 % |
| **at least one marker** | **182** | **36.4 %** |

`SELECT AVG(…) / NULLIF(12, 0)` has no authorial reading: guarding the literal 12 against division
by zero is a mechanical rewrite. `NULLS LAST` occurs 0 times in the SQLite original and 84 times in
the PostgreSQL variant.

### 3.3 The port is bounded, and the boundary is measurable

The SQLite variant was profiled identically and matched on `question_id`. The difference between
the two variants is the converter's contribution.

| | queries | share |
|---|---|---|
| text identical after whitespace normalisation | 202 | 40.4 % |
| text differs | 298 | 59.6 % |
| **structure identical** | **460** | **92.0 %** |
| structure differs | 40 | 8.0 % |

Three fifths of the queries were rewritten textually; nine tenths kept their shape. Of the 40
structural changes, 37 are `CASE`, forced by two SQLite idioms with no PostgreSQL equivalent
(`SUM(status = 'C')` and `IIF`). The reported 19.0 % `CASE` share is therefore inflated by roughly
seven percentage points; human usage is nearer 12 %.

| dimension | status on the PostgreSQL variant |
|---|---|
| **Composition** — nesting, joins, CTEs, subqueries | Usable. 92 % structural identity, deviation isolated to `CASE`. |
| **Operators** — function and operator names | Contaminated. Use the SQLite variant as the human reference. |
| **Logic** — predicate placement, sargability | Usable. 91 % of the signal survives from the original. |

**Consequence for the method.** The dimension carrying most of RQ1 can proceed on the PostgreSQL
variant. The operator comparison moves to the SQLite variant. This is a correction to the plan, not
an obstacle to it.

### 3.4 One in nine reference queries defeats an index

54 queries (10.8 %) wrap a column in a function inside a `WHERE` predicate — the pattern discussed
in July, present in the *human* reference set.

`TO_CHAR` 29 · `SUBSTRING` 15 · `EXTRACT` 9 · `CAST` 6 · `RIGHT` 3 · `DATE` 2 · `LENGTH` 1

49 of the 54 (90.7 %) were already non-sargable in the SQLite original, so this is the author's
phrasing and not a porting artifact.

The schema, however, invites it. In `debit_card_specializing`, `yearmonth.Date` is stored as text,
so `SUBSTR(Date, 1, 4) = '2013'` is the only way to filter by year. This is a property of the data
model rather than an error, and it supports RQ4 directly: whether a predicate can use an index
depends on the schema and the available indexes as much as on the phrasing.

These 54 queries form a ready-made target set for the index-configuration experiments.

### 3.5 The method is viable

500 of 500 queries parsed without failure across 11 databases. The three exposé dimensions map onto
syntax-tree features without strain. The layer needs no database, no container and no model API,
which makes it the cheapest path to a defensible result while the execution layer is still
outstanding.

### 3.6 A paired comparison already runs end to end

BIRD ships no schemas, so no query can be generated against it yet. **Spider 1.0 ships 166 databases
with their schemas**, and was therefore used for a pilot of the whole pipeline: question → model →
generated SQL → execution → comparison with the reference result.

Thirty tasks over twenty databases, seeded selection, two models. A third model returned an API
error and is excluded rather than counted as zero. 89 of 90 SQL records parse.

| Construct | Human | Laguna XS 2.1 | Nemotron Lightning |
|---|---|---|---|
| Nested SELECT | 4 of 30 | 6 of 29 | **9 of 30** |
| Explicit JOIN keywords, mean | 0.67 | 0.69 | **0.53** |
| WHERE clauses, mean | 0.53 | 0.62 | **0.80** |
| Common table expressions | 0 | 0 | 0 |
| Result matched the reference | — | 21 of 30 | 19 of 30 |

One model reaches for subqueries where the human reference joins — the direction Pecuchova and Benko
report, here on a different corpus and with execution-based validation. The other barely differs,
which indicates the effect is model-dependent rather than a property of generated SQL as a class.

**This is a pilot, not a result.** Thirty tasks, one generation run, no repeats; the matched subsets
differ between the two models, so a common-task cohort is needed before the models are compared with
each other. No query anywhere uses a CTE — a limitation of the corpus, not a finding about models.

### 3.7 Formulations that agree on the benchmark diverge under NULLs and ties

Nine counterexample tests were run on in-memory copies, leaving the benchmark untouched.

| Case | Agreement on benchmark data | After one change | Human | Model |
|---|---|---|---|---|
| `NOT IN` vs `NOT EXISTS` | identical rows | add a visit with a NULL museum id | 0 rows | 4 rows |
| `ORDER BY … LIMIT 1` vs `= MAX` | identical rows | make two stadiums tie | 1 row | 2 rows |

Two consequences. A correctness score conceals structural differences that have real effects, which
is the argument for treating correctness as an inclusion criterion rather than a result. And the
reference query is not automatically the right one — the BIRD annotation-error problem, demonstrated
rather than cited.

## 4. Related work

**Pecuchova & Benko, FLAIRS 39 (2026)** — 669 Snowflake queries, 189 human and 480 AI-generated.
They report that models use nested subqueries where humans use joins. The construct comparison is
therefore already published and every novelty claim must be positioned against it.

Two properties of that paper, both verified by full-text search rather than inferred:

1. **Nothing is executed.** EXPLAIN, execution plan, optimizer, index and PostgreSQL each occur
   zero times in the paper. The measurements are code metrics — Halstead volume, cognitive
   complexity. The structural difference is established; its consequences are not examined.
2. **The human baseline is 189 assessment answers from 30 students**, retained when scored at least
   4 of 5. Their own limitations section states that future work should expand the human baseline to
   professional developers.

Their result is therefore the premise of this thesis rather than its competitor, and the argument
for working SQL corpora (SQLShare, Join Order Benchmark, BEAVER) can now be cited as the field's
own stated next step instead of asserted.

Their finding also sits consistently beside the BIRD measurement: two different human populations
on two different platforms both produce structurally plain SQL. This is consistency between
samples, not replication.

## 8. Limitations of what is reported here

- Benchmark gold queries only, on both corpora. Nothing above describes how SQL is written at work;
  that is what the further corpora are for.
- Non-sargability is determined syntactically. Whether an index exists, and whether the planner
  could still use it, requires execution and is not claimed.
- The porting markers are heuristics. `NULLIF` and `NULLS LAST` are legitimate SQL; the inference
  rests on their frequency and on cases such as `NULLIF(12, 0)` that admit no authorial reading.
- Sections 3.1 to 3.5 are text measurements on BIRD; no query there has been executed.
- The Spider pilot of section 3.6 is 30 tasks from one seeded run. It is an existence proof that the
  pipeline works, not an estimate of how often models differ from people.
- Matching the reference result means agreement on the data that happens to be in the database. As
  section 3.7 shows, it is not semantic equivalence.
- No execution plan has been captured and no PostgreSQL measurement has been made.
